A dedicated log table must be created in the database to capture all Gen AI events triggered across the application.
The following fields must be stored for every audit log entry:
User (the user who triggered the event)
Step (e.g., Capability Setup, AI Identifier, Impact Analyzer, AI Prioritization, Capability Double Click, CDC Step)
Sub step (e.g., L3 Capabilities Opex, Generate L2 Capabilities, Generate L3 Capabilities; nullable where not applicable)
Progress % (numeric value representing the completion percentage at the time of logging)
Status (e.g., In Progress, Success, Failed, Cancelled)
Timestamp (date and time the event was triggered, stored in UTC)
A new record must be inserted into the audit log table every time a Gen AI event is triggered, regardless of its outcome.
The status field must be updated in real time as the event progresses (e.g., from In Progress → Success or Failed).
The progress % field must be updated incrementally as the event advances, reflecting the latest known completion state.
If a Gen AI event is cancelled mid-execution, the audit log record must capture the progress % at the point of cancellation along with a Cancelled status.
If a Gen AI event fails, the audit log record must be updated to reflect the Failed status and the progress % reached before failure.
The sub step field must allow null values for steps that do not have an associated sub step.
The timestamp must be recorded at the moment the event is initiated, not at completion.
The audit log table must not be used for any delete operations — records must be retained permanently for traceability.

No front-end integration is in scope at this time; the requirement is limited to backend data capture and DB storage only.
The audit log table must be queryable by any combination of user, step, sub step, status, and timestamp range to support future reporting needs.
