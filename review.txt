**What I verified**

- In the `/twobytwo` path, `items_to_batch` is `selected_capability_map`; each `_evaluate_batch()` receives a slice of that list, and passes the slice to `evaluate_feasibility_viability()` (batching, 2x2 batch call, `two_by_two_generator.py:736`). There, `unique_ids` are derived from that same list (`two_by_two_generator.py:672`). So for `/twobytwo`, `selected_capability_map` at `_build_prompt()` is the current batch.
- That path gets the selection from decoded persisted JSON, so its entries are plain dictionaries, not Pydantic models ([map selection](apis/v1/two_by_two.py#L181)). The `SelectedCapabilityMap` schema requires `l1CapabilityName` and `uniqueId`, and defines `l2CapabilityName`/`l3CapabilityName` as optional (`two_by_two_generator.py:38`). Since `/twobytwo` does not validate this JSON against that model, I cannot confirm every persisted entry actually contains all four keys. Missing hierarchy names will resolve to “not available.”
- Capability Double Click differs: it batches the current-level capability list, but passes the primary `selected_capability_map` rather than the batch to `_build_prompt()` ([CDC batch setup](agents/two_by_two/two_by_two_generator.py#L935), `two_by_two_generator.py:944`). Thus the current-capability filtering loop must remain for that path.
- In `/twobytwo`, ID values are read from the same batch objects for `unique_ids`; they are not converted. In CDC’s fallback, IDs come from the overridden batch and are compared to those same capability dictionaries. No code validates uniqueness, so duplicate IDs are possible in supplied data; I cannot confirm whether persisted production data contains them.
- The 2x2 `_build_prompt()` has one call site, in `evaluate_feasibility_viability()` (definition, call); I found no 2x2 test call site. The other `_build_prompt()` matches are in the separate industry-classification module/tests.
