## Summary
L1/L2 OpEx generation could stay stuck in loading / at 5% forever. When the
background job failed, the exception handler never reported it: the guard
`"substepkey" in locals()` was always false, so the failed DB status and the
Redis "Error" event were never sent and the UI kept waiting.

## Changes (apis/v1/agentic_fit_allocator.py – exception handler only)
- Use the real substepkey/input_key (job metadata, falling back to the payload)
  for the failed status write and the Error event.
- Safe defaults for action/client_info/receiver_email/channel when the failure
  happens early.
- Failed-status DB write is best-effort (own try/except); sub_step_name is only
  sent when available (early failures previously hit a NOT NULL violation and
  crashed the handler).
- Redis "Error" event is always published, regardless of the DB write.
- No changes to the success path.

## Root cause context
On dummy projects Total OpEx is empty (no client data), so generation fails
without it. That failure was hidden by the handler bug, so the UI stayed stuck.
With Total OpEx entered, L1 and L2 complete.
