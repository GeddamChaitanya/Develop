2x2: add High Fit % and Cost Saving Opportunity as dimension-scoring context

## Summary
Implements the "Existing 2x2 Enhancement" part of the Fit vs Dollar PBI. When the LLM scores each viability and feasibility dimension, it now also receives each capability's existing High Fit % and Cost Saving Opportunity, taken from the saved AI Identifier / Workforce Analyzer output (Cost Saving Potential). The existing context (survey, file, workspace, industry), the rubric, the weights and the viability/feasibility calculation are unchanged.

## Changes
- `apis/v1/capability_double_click.py`: moved the loading part of `_load_impact_analyzer_for_process()` into a new `_load_cost_saving_potential_output(process_key)`, which returns the saved output. The original function calls it, so Capability Double Click behavior and return values are unchanged.
- `agents/two_by_two/fit_cost_enrichment.py` (new): pure functions that
  - build a read-only lookup keyed by the normalized L1/L2/L3 name path (L1/L2 from `Cost Saving Potential.l1_l2_heatmap`, L3 from `impact_analyzer`),
  - return the values for a capability,
  - format one prompt line per capability.
- `apis/v1/two_by_two.py`: loads the saved output by `processKey` just before scoring and passes the lookup to the scorer. With no process key or no saved output, the 2x2 runs exactly as before.
- `agents/two_by_two/two_by_two_generator.py`: optional `fit_cost_lookup` parameter (default `None`) passed through `generate_two_by_two_analysis` → `_evaluate_batch` → `evaluate_feasibility_viability` → `_build_prompt`. `_build_prompt` adds a per-batch "CAPABILITY FIT AND COST-SAVING CONTEXT" block after the client context block.
- `tests/test_two_by_two_fit_cost.py` (new): 25 regression tests on mock data.

## Design notes
- **Read-only lookup:** capability dicts are not modified, so nothing leaks into stored output or later steps.
- **No recalculation:** saved values are used as they are. Zero is treated as a valid value; missing or ambiguous values show "not available".
- **Matching on the full L1/L2/L3 path,** not the L3 name only. Duplicate paths are treated as ambiguous and logged once.
- **Batch-scoped:** each LLM batch only receives the lines for its own capabilities. IDs are compared as strings.
- **Both flows covered:** AI Identifier and Workforce Analyzer save the same structure, so one code path handles both.
- The 2x2 branch inside the Capability Double Click endpoint was intentionally not changed. It currently always fails at `response["current_state"]` (pre-existing), so production 2x2 traffic uses `/twobytwo`.

## Testing
- **Unit tests:** `tests/test_two_by_two_fit_cost.py`, 25 tests, all passing. They cover both pipeline shapes, root-level `impact_analyzer`, alternative L3 name keys, name normalization, duplicate and ambiguous paths, zero values, batch filtering, string vs numeric IDs, no-lookup (unchanged prompt), and the CDC loader refactor.
- **Existing tests:** related 2x2/CDC tests pass. One pre-existing failure, unrelated (also fails on `ascend/develop`): `test_cdc_status.py::test_two_by_two_path_sets_status_complete`.
- **Smoke tested `/twobytwo` locally against dev:**
  - **Workforce (process 98): L1, L2, L3.** Correct values matched by the full path (e.g. L3 Regulatory Reporting: 43% / 3,491,356), the block was present in the prompt, the values were used in the reasoning, and the jobs completed and saved normally.
  - **No-data fallback (process 85, AI Identifier output blob missing):** no block was added, and the 2x2 ran exactly as before.
  - **AI Identifier happy path:** covered by unit tests; to be confirmed on a fresh process (Ascend dev UI currently unavailable).

## Open questions for review
1. The LLM sometimes reads High Fit % as "% opex reduction" (e.g. 43% fit, so >40% cost reduction, so VERY HIGH). Should the block add a one-line definition of each metric?
2. Workforce L3 cost values arrive as raw floats (e.g. 3491356.2974999994). Should they be rounded in the prompt text only?
