## AI Identifier Flow

The dedicated Agentic Fit 2x2 entry point is `POST /api/v1/twobytwo`: `two_by_two.py:41` accepts `AgenticFitAllocatorInput` (`two_by_two.py:43`), reads `L3_capability_map` from the saved input JSON, and passes the L1/L2/L3 maps to `generate_two_by_two_analysis()` (`two_by_two.py:183`, `two_by_two.py:249`). So yes, that route is the AgenticFitAllocatorInput-based path. The repo does not show the allocator calling that route directly; the map arrives through the persisted request input.

The allocator’s L3 output is converted to numeric `"High Fit %"` and `"Cost Saving Opportunity"` in `agentic_fit_allocator.py:917`. Its L1/L2 heatmap values are also produced (`L1_percent`/`L1_amount`, `L2_percent`/`L2_amount`) ([heatmap aggregation](apis/v1/agentic_fit_allocator.py#L1920)). But `/twobytwo` itself does not load or merge that saved output: it passes through the `L3_capability_map` it read. The explicit bridge is instead in `capability_double_click.py:422`: its enrichment maps `"High Fit %"` to `High_Fit_%` and `"Cost Saving Opportunity"` to `Cost_Saving_Opportunity` ([field map](apis/v1/capability_double_click.py#L177)), then calls the shared scorer (`capability_double_click.py:514`). That loader only extracts `impact_analyzer` rows (`capability_double_click.py:60`); it does not pass the heatmap rollups into L1/L2 capabilities.

## Workforce Analyzer Flow

The Workforce Analyzer endpoint builds and saves its own result; it does not call the 2x2 scorer in that handler (`workforce_analyzer.py:205`, `workforce_analyzer.py:909`). Its L3 rows contain numeric `"High Fit %"` and `"Cost Saving Opportunity (USD)"` values (`workforce_analyzer.py:1571`, `workforce_analyzer.py:1577`). `build_l1_allocations()` and `build_l2_allocations()` roll up numeric `high_fit_percentage` and `cost_saving_opportunity` values (`workforce_analyzer.py:1794`, `workforce_analyzer.py:1849`, `workforce_analyzer.py:1866`, `workforce_analyzer.py:1923`).

The later `/capability_double_click` route loads the process’s cost-potential output and enriches only its L3 capability maps ([loader and enrichment call](apis/v1/capability_double_click.py#L434)). Its shared field map converts `"High Fit %"` to `High_Fit_%` and `"Cost Saving Opportunity (USD)"` to `Cost_Saving_Opportunity` ([field map](apis/v1/capability_double_click.py#L177)). The Workforce Analyzer rollups are in `WorkforceAnalyzerGrid`, but the loader’s extractor reads only `Cost Saving Potential.impact_analyzer`; it does not merge `l1_allocations` or `l2_allocations` into the 2x2 capability data (`capability_double_click.py:60`).

**Shared code:** Both paths ultimately call `generate_two_by_two_analysis()`. The explicit bridge for saved Agentic Fit and Workforce Analyzer values is currently the enrichment code in `capability_double_click.py`; its field map already handles both pipelines’ different cost-saving keys. The separate `/two_by_two_generator` route is also registered (`two_by_two_generator.py:18`), but neither flow’s code shown here calls it. The enrichment lookup matches on normalized L3 name, not `uniqueId` or the full L1/L2/L3 path (`capability_double_click.py:60`).
