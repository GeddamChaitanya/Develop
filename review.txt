## Routes and Steps

All routes are registered under the `/api/v1` prefix in `base.py:23`. The three relevant routes are:

- **`POST /api/v1/twobytwo`** is an async, DB-backed route accepting `AgenticFitAllocatorInput` (`two_by_two.py:43`). It reads its Redis channel from `REDIS_channel_name_twobytwo` (`two_by_two.py:126`); the local config sets that to `two_by_two_background_process` (`run.ps1:16`). The docs call this the background-processing variant ([API docs](docs/genai_attribution_report.md#L704)).
- **`POST /api/v1/capability_double_click`** is an async, DB-backed CDC route, also accepting `AgenticFitAllocatorInput` (`capability_double_click.py:248`). It uses `REDIS_channel_name_capability_double_click` (`capability_double_click.py:335`); local config sets it to `capability_double_click_background_process` (`run.ps1:25`). Its documented purpose is a capability deep-dive, including KPIs and current/future state ([API docs](docs/genai_attribution_report.md#L723)).
- **`POST /api/v1/two_by_two_generator`** is a separate synchronous route accepting `TwoByTwoGeneratorInput` (`two_by_two_generator.py:18`). Its documentation describes it as stateless and supports both the viability-feasibility and capability-double-click step names ([API docs](docs/genai_attribution_report.md#L664)).

Both `TWO_BY_TWO_STEP_NAME` and `CAPILITY_DOUBLE_CLICK_STEP_NAME` are handled by the shared scorer and the async `/twobytwo` endpoint (`constants.py:9`, `constants.py:10`, `two_by_two.py:267`). The CDC endpoint calls the scorer too, with branches for both step names (`capability_double_click.py:526`).
