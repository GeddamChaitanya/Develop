## Persistence and Matching

Both outputs use `blueprinting_process_sub_step_output`, whose relevant columns include `sub_step_key`, `generated_for_input_key`, `output_json`, `output_file_storage_name`, and `output_file_path` ([output model](db/models.py#L195)).

- **AI Identifier:** saves `{"Cost Saving Potential": ...}` to blob storage; the database row has `output_json: None` and stores the blob path (`agentic_fit_allocator.py:667`, `agentic_fit_allocator.py:689`). Its `_load_persisted_output()` helper reads inline JSON or falls back to the blob (`agentic_fit_allocator.py:166`).
- **Workforce Analyzer:** saves `{"Cost Saving Potential": ..., "WorkforceAnalyzerGrid": ...}` inline in `output_json`, with `is_output_json: True` (`workforce_analyzer.py:909`, `workforce_analyzer.py:920`).

There is no direct `db` reader for these outputs by project key or capability. The generic readers are `read_sub_step_output_by_output_key()` and `read_latest_sub_step_output_by_input_key(input_key, sub_step_key=None)` ([output-key reader](db/db_operations_orm.py#L930), `db_operations_orm.py:961`). The project-key reader is for capability maps, not saved cost-saving outputs (`db_operations_orm.py:983`).

There is an existing process-level loader in the API: `_load_impact_analyzer_for_process(process_key)` searches recent Workforce and OPEX Cost Saving Potential outputs and handles inline JSON or blob storage (`capability_double_click.py:90`). It builds a lookup by normalized **L3 name only** ([lookup construction](apis/v1/capability_double_click.py#L60)); its enrichment code maps both pipelines’ field-name variants to `High_Fit_%` and `Cost_Saving_Opportunity` ([field mapping](apis/v1/capability_double_click.py#L153)).

Saved rows do **not** contain the 2x2 request’s `uniqueId`. AI Identifier adds UUID row IDs ([ID utility](utilities/unique_id.py#L5)); Workforce Analyzer assigns generated row IDs ([L3 row IDs](agents/workforce_analyzer/workforce_analyzer.py#L1585)). For joining a saved row to the 2x2 request, use the full `(L1, L2, L3)` name path: saved rows have those three names, while the request models expose the corresponding capability names ([2x2 models](schemas/two_by_two_generator.py#L49)).

## 2x2 Check

The L1 and L2 request models have neither fit nor cost-saving fields. L3 has optional numeric `High_Fit_percent` with alias `High_Fit_%`, but no Cost Saving Opportunity field ([L1/L2/L3 models](schemas/two_by_two_generator.py#L49), `two_by_two_generator.py:71`). `CapabilityKPI` has a separate required numeric `cost_saving_opportunity` output field; it is not an L1/L2/L3 map input (`two_by_two_generator.py:140`).

In this branch, the async context fetchers **are awaited** ([survey and file fetches](apis/v1/two_by_two_generator.py#L59)). The call arguments therefore do **not** match; the unexpected keyword will raise an error.
